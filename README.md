# Cloud Runtime Guardian

A **working**, single-node cloud-runtime security prototype in Go. It correlates process execution with outbound connections within a single workload and produces explainable incidents.

**Current status:** single-node runtime detection/control-plane preview. A Tetragon JSONL collector exists, but the repository does not include an eBPF sensor or a fully validated Kubernetes deployment. Active enforcement is disabled. The incident response endpoint is intentionally **dry-run only**. Test events are generated by the simulator or submitted through the API. The architecture is deliberately small enough to run on a development laptop.


## Containment: manual, expiring, and disabled by default

This version includes a durable state machine for containment requests, a simulator,
and an **experimental** Kubernetes NetworkPolicy backend. Administrators must
explicitly request a **pod-wide** isolation and set a 60..3600-second TTL;
no detection can apply a policy on its own. Every transition is fsynced and
replayable. The controller retries after outages and a separate Kubernetes
CronJob can remove expired NetworkPolicies if the main server is unavailable.

The containment backend is **off by default**. It has mock-Kubernetes tests,
not validated production-CNI behavior. See
[containment safety and deployment guide](docs/containment.md).

## Kubernetes-verified ingestion (opt-in, preview)

A strict node-ingestion mode is now available. It authenticates each collector with
its own node-bound token and verifies pod UID, container ID, node placement and
pod deletion state against the live Kubernetes API before durable ingestion.
The feature requires `CRG_K8S_VERIFY=1`, HTTPS, a private
`CRG_NODE_CREDENTIALS_FILE`, an administrator token, and a Kubernetes service
account permitted to `get` pods. It rejects stale pods and fails closed when
identity cannot be verified. Source authentication is **not** hardware attestation.

See [Kubernetes identity deployment and threat model](docs/kubernetes-identity.md)
and the templates `deploy/kubernetes/identity-rbac.yaml` and
`deploy/kubernetes/server.yaml`. No real-cluster validation has yet been done.

## Run it

Prerequisite: **Go 1.23+** to run locally; use a supported, patched Go release for actual deployment (CI builds with Go 1.26). No database, Docker, privileged permissions, or third-party Go packages required.

Terminal 1:

```sh
go run ./cmd/server -addr 127.0.0.1:8080 -data ./data/journal.jsonl
```

Terminal 2:

```sh
go run ./cmd/simulate
curl -s http://127.0.0.1:8080/v1/incidents
curl -s http://127.0.0.1:8080/v1/stats
```

The simulator posts a network connection **before** an earlier-in-event-time shell execution. The correlator should still create one incident. No simulated destination is contacted; the simulator sends metadata exclusively to the local API.

Run the full suite, including concurrency instrumentation:

```sh
go test ./...
go test -race ./...
```

The server uses a newline-terminated append-only JSONL journal, fsyncs accepted writes, and replays incidents and dry-run actions on restart. To reset the local demo, stop the server and remove `./data/journal.jsonl`.

## HTTP endpoints

| Verb | Path | Purpose |
| --- | --- | --- |
| `GET` | `/healthz` | Liveness |
| `POST` | `/v1/events` | Validate and durably ingest an event (`202` created, `200` duplicate, `409` conflicting ID) |
| `GET` | `/v1/incidents?limit=100&offset=0` | Indexed incident listing with numeric offset |
| `GET` | `/v1/incidents?limit=100&cursor=` | Stable, opaque keyset pagination; follow `next_cursor` |
| `GET` | `/v1/incidents/{id}` | Incident + immutable evidence and response history |
| `POST` | `/v1/incidents/{id}/response` | Record a **dry-run** containment proposal; no network changes |
| `GET` | `/v1/stats` | Event / incident / response / containment counts and capacity |
| `POST` | `/v1/incidents/{id}/containment` | Manually queue a time-bounded pod-wide containment; requires admin credentials and explicit server opt-in |
| `GET` | `/v1/containments` | Inspect containment state and audit metadata |
| `GET` | `/v1/containments/{id}` | Inspect one recorded containment |
| `DELETE` | `/v1/containments/{id}` | Durably request release and eventual reconciliation |

An example request pair is in [`examples/events.jsonl`](examples/events.jsonl). Send individual lines, not a JSONL document, to `/v1/events`. See [`docs/architecture.md`](docs/architecture.md) for the event contract and rule logic.

Example response proposal (substitute an actual incident ID):

```sh
curl -X POST 'http://127.0.0.1:8080/v1/incidents/INCIDENT_ID/response' \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"review-0001","action":"block_workload_egress","reason":"Analyst review before any real enforcement"}'
```

The response always includes `"mode":"dry_run"` and `"enforcement_applied":false`.

## Security defaults

- The server listens **only on 127.0.0.1** by default.
- To listen on a non-loopback address, configure **distinct** `CRG_INGEST_TOKEN` and `CRG_ADMIN_TOKEN` (minimum 24 characters each), and serve HTTPS with `-tls-cert` / `-tls-key`. The legacy `CRG_API_TOKEN` is for loopback development only; bearer credentials are not workload identity/RBAC.
- JSON input is size-limited (32 KiB), unknown properties are rejected, and event identifiers are validated.
- Event IDs and response request IDs are idempotency keys and remain effective after restart. Reusing an ID with different content returns `409`.
- The legacy `/response` endpoint is always dry-run. The separate containment endpoints can alter Kubernetes policies **only** when an operator explicitly opts in, requires a dedicated admin credential, and enables strict verified workload identity.
- The ledger is created with restrictive permissions. If a committed journal record is corrupt, the service refuses startup rather than silently discarding audit data.

**Do not deploy as a production EDR/runtime prevention product.** For credential separation, HTTPS, persistent storage, and container guidance, see [`docs/operations.md`](docs/operations.md). See [`docs/threat-model.md`](docs/threat-model.md) and the limitations below.

## Current limitations

1. External Tetragon is required for real kernel telemetry; this repository contains a JSONL bridge, not a full sensor.
2. The detector has one heuristic behavioral rule. It is not an antivirus or full runtime prevention platform.
3. The single-writer segmented WAL and offline snapshots are bounded by configured replay capacity; there is no multi-node high-availability database.
4. Kubernetes event-source verification is opt-in; bearer credentials are not node attestation.
5. Containment is disabled unless explicitly configured. The experimental Kubernetes backend has no live-cluster/CNI validation and blocks an entire pod, not just one container. Independent expiry cleanup is best effort.
6. No full-scale throughput, multi-node recovery, policy convergence, or pod-churn benchmark has been completed in a real cluster.

Review [containment](docs/containment.md), [operations](docs/operations.md), and [identity](docs/kubernetes-identity.md) before deploying.

## Development

The Go standard library is the only dependency. `internal/engine` owns replay-safe correlation; `internal/journal` owns durability; `internal/httpapi` owns API parsing and transport. No runtime component attempts to modify machine/network state.

## Linux Tetragon live telemetry bridge

The new `cmd/collector` reads a **local, append-only Tetragon JSONL export** and
forwards `process_exec` and `process_connect` to `/v1/events`. It uses the
Linux kernel boot ID, stable Tetragon `exec_id`, node-name checks, container
identity, deterministic event IDs, HTTP acknowledgment and fsynced per-record
checkpoints. Non-retryable API rejections and source truncation/rotation stop
the collector instead of silently losing records. TLS is required when sending
to remote IPs. See [Tetragon source notes](examples/tetragon/README.md).

This is a **tested ingestion bridge, not production-ready EDR**. The exporter
must be configured to emit connect events; host-node name and boot epoch must
match. Automatic rotation recovery, HA event queues, policy-based filtering,
large-volume indexing, authentication beyond one bearer token, complete
observability/alerting, and real containment remain unimplemented. The
checkpoint is on the same local disk; operators must supervise and retain
export logs until ingestion is confirmed. The fail-closed approach prioritizes
correctness over availability.

## Reliability and operations (development)

The collector now supports **single, unambiguous rename/create rotation**, including
restart recovery from a retained archive. It refuses missing or multiple archives,
incomplete rotated records and `copytruncate`; it does not silently jump over
unprocessed intermediate files. `ArchiveGlob` defaults to `export + ".*"`; archives
must be kept until acknowledged. Multi-rotation durability requires a real
rotation manifest or streaming cursor and remains a **production blocker**.

The service provides unauthenticated `GET /healthz` (process liveness) and
`GET /readyz` (ledger writable and below capacity). `GET /metrics` emits
Prometheus-compatible gauges and uses normal API bearer-token protection.
Read the [cluster readiness runbook](docs/cluster-readiness.md) before deploying.

## Recent storage and security hardening

- Exclusive journal writer lock, secure regular-file opening, replay limits and
  strict journal parsing. A second writer fails to start instead of corrupting
  the ledger. Event fan-out cannot exceed the incident-capacity budget.
- Separate `CRG_INGEST_TOKEN` / `CRG_ADMIN_TOKEN` privileges. Non-loopback
  listeners require distinct credentials **and native TLS** (certificate and
  private key flags); loopback-only mode stays convenient for local testing.
- Multi-stage Linux container build, single-replica Kubernetes template,
  benchmark test and [operations runbook](docs/operations.md).
- **Not yet production certified:** container build and Kubernetes lifecycle
  require real runtime verification; no high-availability/retention solution,
  authenticated workload identity, live enforcement, or real sensor validation.

## Indexed investigations and fault-injection tests

New incidents are indexed by `(first_seen DESC, id ASC)` with an AVL tree.
`GET /v1/incidents?limit=50&cursor=` returns `next_cursor` when more rows
are available. Subsequent pages use `?limit=50&cursor=<next_cursor>`; do
not combine `cursor` and `offset`. Invalid cursors return `400`.
Existing `offset` pagination remains backwards-compatible. Cursor pages
remain stable when newer events arrive; deletion/retention is not supported.
The index is **reconstructed from fsynced journal entries after restart**;
there is no separate index file to get out of sync with the ledger.

`go test -race ./...` includes a killed-writer subprocess test on Linux,
external journal replacement/truncation tests, malformed JSON replay tests,
randomized indexed-pagination checks, API cursor tests, and journal restart
recovery. `go test ./internal/incidentindex -run TestOrderedPaginationAndDedup -count=1`
checks large randomized orderings. These tests do not simulate a power-loss
filesystem or establish high-availability guarantees.

### Segmented durable WAL (offline compaction milestone)

New journal writes roll into numbered, fsynced WAL segments after 8 MiB.
Existing `journal.jsonl` files remain readable without destructive migration.
All segments are replayed and verified on restart, with missing-segment
checks. To verify or losslessly gzip-compress closed segments **while the
server is stopped**, run:

```sh
go run ./cmd/ledgerctl -data ./data/journal.jsonl
go run ./cmd/ledgerctl -data ./data/journal.jsonl -compact-closed
```

Keep `journal.jsonl` **and** its `journal.jsonl.segments/` directory together
for backup/restore. **This does not implement expiry or retention deletion:**
archival retains all records and idempotency history. See
[`docs/operations.md`](docs/operations.md) for crash recovery and limits.

## Verifiable offline backups (snapshot milestone)

The new `cmd/ledgerctl` can create authenticated-by-checksum offline backups
of the base journal and all WAL segments, verify them, restore into a **new**
folder, and keep a bounded number of verified backup archives. Backup creation
requires stopping the server because it acquires the same exclusive ledger
lock. This is a complete-ledger archival snapshot, not a serialized engine-state
snapshot; WAL retention and startup replay remain unchanged.

```sh
mkdir -p backups && chmod 700 backups
# Stop the server before this command:
go run ./cmd/ledgerctl -data ./data/journal.jsonl \
  -snapshot ./backups/crg-001.crg-snapshot.zip

go run ./cmd/ledgerctl -verify-snapshot ./backups/crg-001.crg-snapshot.zip

go run ./cmd/ledgerctl -restore-snapshot ./backups/crg-001.crg-snapshot.zip \
  -restore-dir ./restored-001

go run ./cmd/ledgerctl -prune-snapshots-dir ./backups -keep-snapshots 3
```

See [operations runbook](docs/operations.md#offline-verified-snapshot-restore-and-backup-retention)
for safety boundaries, permissions, and recovery procedures. Archive checksums
do not provide confidentiality or authenticate the archive against an attacker
who can replace the ZIP and its manifest; store it in trusted, access-controlled
(and ideally encrypted) backup storage. Cluster-validated operations and
high-availability storage remain future work.
